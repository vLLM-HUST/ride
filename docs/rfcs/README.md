# RIDE RFC 索引与评审规范

RFC（Request for Comments）用于评审跨仓库接口、控制语义、重要策略和生命周期变更。它记录问题、选型与取舍，不是实验结果或运行授权。本文是本项目约定的格式，不声称存在适用于所有项目的统一RFC模板。

## 编号与位置

- 跨Controller/RIDE设计统一保存在本目录，文件名`NNNN-topic.md`，编号单调递增，不回收旧编号。
- 使用[TEMPLATE.md](TEMPLATE.md)，新增RFC同时更新下表。各独立仓库引用同一RFC，不复制另一份设计。
- 规划记录目标与顺序，RFC记录设计决策，[效果契约](../architecture/CONTROLLER_EVALUATION.md)记录测量方法，[统一路线图](../architecture/CONTROLLER_ROADMAP.md)记录实现状态。数据、实测结论与原始证据按组织规范归benchmark仓库；RFC只保留必要链接。

## 状态与决定

文档评审状态为`Draft → In Review → Accepted / Rejected / Withdrawn`；被新设计替代后标`Superseded`并链接后继RFC。这些只表示文档评审，不替代实验的PASS/FAIL/NOT_RUN等执行状态。

作者提出草案；决策人及受影响接口的维护者评审范围、兼容性、安全性和验证方法。进入Accepted必须记录明确的决定人、日期、接受的修订和遗留条件；不得根据沉默、代码已写或测试通过推断接受。评审者未指定时如实记录，不代签其他人。

Accepted不等于已实现，已实现不等于已部署或有效。实现状态只在路线图维护。RFC不自动授权平台资源、运行实验、合并代码或对外发布；现有具体授权与部署规范继续适用。

## 内容要求

每份RFC必须自包含：问题和运行例子、目标/非目标、已有工作与证据边界、所选设计和不变式、对象/API/数据口径、决策与执行流程、失败恢复、兼容和回退、可观测性、安全/资源边界、验证、分阶段交付、替代方案、未决问题及决策记录。

“必须”表示接受该设计后实现/验收不可省略的约束；“建议”表示可说明理由后调整的选择；“可选”不得默认为已启用。示例数据和拟议API必须明确标注，不充运行回执。无法完成的决定列明推荐立场、影响及决定人，不用无内容的TODO替代设计。

修改已接受RFC的接口或语义时重新评审，并保留旧决定；不静默改写已执行实验的参数或门槛。审阅时逐项问：为什么需要、观测是否可取得、动作是否真正生效、失败后会怎样、如何证明有效、代价在哪里。
